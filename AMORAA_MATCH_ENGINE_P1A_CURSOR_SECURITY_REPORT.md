## 1. Executive Summary

Phase 3 P1-A of the AMORAA Match Engine Master Execution Plan required replacing the plaintext base64url HMAC recommendation pagination cursor with authenticated, opaque symmetric encryption using AES-256-GCM. 

The previous cursor format (`<base64url_json_payload>.<hmac_signature>`) allowed clients or network intermediaries to inspect ranking scores, internal candidate IDs, viewer IDs, and active filters.

P1-A has successfully replaced this with a versioned, authenticated, opaque AEAD token:
- **Algorithm:** AES-256-GCM with 12-byte cryptographically random IV and 16-byte authentication tag.
- **Wire Format:** `c2.<kid>.<iv_base64url>.<ciphertext_base64url>.<tag_base64url>`
- **Associated Data (AAD):** Cryptographically bound to the cursor format version, key ID, viewer user ID, and recommendation surface (`c2:${kid}:${viewerId}:${surface}`).
- **Key Management:** Dedicated 32-byte `CURSOR_ENCRYPTION_SECRET` decoupled entirely from `JWT_SECRET`, with multi-key rotation keyring support via `CURSOR_PREVIOUS_SECRETS`.
- **Validation & Tamper Resistance:** Comprehensive fail-closed error handling with specific domain codes (`PAGINATION_CURSOR_INVALID`, `PAGINATION_CURSOR_EXPIRED`, `PAGINATION_CONTEXT_CHANGED`).
- **Test Results:** 22/22 unit tests passing, full regression test suites passing.

## 2. Cryptographic Architecture & Design Refinements

### 2.1 Encryption & AEAD Construction
- **Cipher:** `aes-256-gcm` provided natively by Node.js `crypto`.
- **Initialization Vector (IV):** 12 bytes generated per token via `crypto.randomBytes(12)`. Uniqueness is guaranteed for every single call. Two identical requests for the same page generate distinct ciphertexts.
- **Authentication Tag:** 16 bytes generated by `cipher.getAuthTag()` and verified by `decipher.setAuthTag(tag)` in constant-time hardware/C++ implementation.
- **Additional Authenticated Data (AAD):** `Buffer.from(`${version}:${kid}:${viewerId}:${surface}`, 'utf8')`. This cryptographically ensures:
  1. A cursor issued for User A cannot be decrypted or submitted by User B (cross-viewer replay prevention).
  2. A cursor issued for Discover feed cannot be used for AI Matches or other surfaces (cross-surface replay prevention).
  3. A cursor encrypted under Key A cannot be manipulated to read under Key B.

### 2.2 Token Format
Tokens conform to the versioned dot-delimited format:
```
c2.<kid>.<iv_base64url>.<ciphertext_base64url>.<tag_base64url>
```
1. `c2`: Cursor format version indicator (Cursor Version 2).
2. `<kid>`: Key identifier (default `'k1'`) designating which secret in the keyring encrypted the payload.
3. `<iv_base64url>`: URL-safe base64 encoded 12-byte initialization vector.
4. `<ciphertext_base64url>`: URL-safe base64 encoded encrypted JSON payload.
5. `<tag_base64url>`: URL-safe base64 encoded 16-byte authentication tag.

Legacy 2-part tokens (`payload.sig`) or `c1` cursors are safely rejected with `PAGINATION_CURSOR_EXPIRED`, prompting the client to refresh the first page gracefully without 500 errors.

### 2.3 Key Management & Keyring Rotation
- **Dedicated Secret:** `CURSOR_ENCRYPTION_SECRET` is strictly separate from `JWT_SECRET`, `JWT_REFRESH_SECRET`, and `ADMIN_JWT_SECRET`.
- **Key Derivation/Reuse Prohibition:** Key deriving from `JWT_SECRET` is strictly forbidden and prevented in code.
- **Key Encoding Support:** Supports either 64-character hexadecimal (32 raw bytes) or 32-character raw ASCII/utf8 strings.
- **Local Dev Autogeneration:** In `Backend/src/config/bootstrapEnv.js`, local development environments automatically generate a dedicated 32-byte cryptographically secure hex secret if empty or placeholder.
- **Staging / Production Enforcment:** In `staging` and `production`, placeholder values (`changeme`, `replace-me`, etc.) immediately throw a fatal configuration error on startup.
- **Multi-Key Ring (`CURSOR_PREVIOUS_SECRETS`):** Supports seamless zero-downtime key rotation. The active key (`CURSOR_ENCRYPTION_KID`, default `k1`) encrypts all new cursors. Historical keys are passed via `CURSOR_PREVIOUS_SECRETS="k0:secret0,k1:secret1"`. Old cursors decrypt cleanly until expired; all new cursors are encrypted with the active key.

### 2.4 Payload Integrity & Context Binding
The encrypted plaintext JSON payload contains:
```json
{
  "v": 2,
  "r": "v2:cursor-2",
  "u": "123",
  "s": "discover",
  "c": "<sha256_base64url_of_context>",
  "k": { "score": 85.5, "id": 456 },
  "iat": 1730550000000,
  "exp": 1730636400000
}
```
- **Context Fingerprint (`c`):** Deterministic SHA-256 hash of normalized filters and viewer state. If the user changes filters mid-pagination, `PAGINATION_CONTEXT_CHANGED` is returned.
- **Timestamps (`iat`, `exp`):** Verified against `Date.now()` with 60-second clock skew tolerance.
- **Max TTL:** Cursors are capped at 24 hours (`MAX_CURSOR_TTL_MS`). Any token requesting a larger lifespan is rejected.
- **Ranking Keys (`k`):** Validated to require numeric finite values with positive integer candidate `id`, score ranges [0, 100], and distance >= 0.

## 5. Key Rotation Operational Guide

To rotate the `CURSOR_ENCRYPTION_SECRET` without invalidating active user sessions or failing ongoing pagination:

1. **Generate New Secret:**
   ```bash
   node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
   ```
2. **Promote New Key & Retain Previous Key:**
   Update the deployment environment (e.g. AWS SSM, Docker secrets, or staging `.env`):
   ```env
   CURSOR_ENCRYPTION_KID=k2
   CURSOR_ENCRYPTION_SECRET=<newly-generated-hex-secret>
   CURSOR_PREVIOUS_SECRETS="k1:<previous-secret>"
   ```
3. **Deploy:**
   Deploy the updated configuration.
   - Any client sending a cursor with `c2.k1...` will be read and decrypted using the previous key `k1`.
   - The server response will generate `nextCursor` encrypted under `k2` (`c2.k2...`).
4. **Decommission Old Key:**
   After 24 hours (maximum cursor TTL), remove `CURSOR_PREVIOUS_SECRETS`:
   ```env
   CURSOR_ENCRYPTION_KID=k2
   CURSOR_ENCRYPTION_SECRET=<newly-generated-hex-secret>
   CURSOR_PREVIOUS_SECRETS=
   ```
