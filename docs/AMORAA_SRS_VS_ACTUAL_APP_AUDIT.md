# AMORAA SRS vs Actual Application Audit

**Snapshot audited:** 2026-09-24; repository `D:\Projects\amora_ai`. SRS: `Amora_SRS (1).pdf`, version 1.0, 22 pages. The audit is against the checked-out source, including pre-existing working-tree changes. This audit made no application changes and did not run tests.

## 1. Executive Summary

The supplied SRS has 30 functional modules and two roadmap items. All SRS table elements, including headings and wrapped entries, are extracted in §5. Status means code-grounded flow coverage, not proof of deployed credentials or production delivery. Partial or disabled flows are not counted as end-to-end complete.

Key findings:

- Onboarding `preferredDistance` and Discover `maxDistanceKm` are stored but do not constrain candidate eligibility or ranking. No user latitude/longitude or distance calculation is used in Discover.
- Authentication has email/password login, Google sign-in, phone OTP account verification, and email recovery; there is no mobile/password or OTP login although SRS Login includes those options.
- Events APIs and screens exist, but `AppFeatureFlags.eventsEnabled` is compile-time `false`; ordinary user entry points are hidden.
- AI recommendations use deterministic JavaScript with provider `LOCAL`; no external/model-backed AI exists. Candidate user ID, match ID, and conversation ID remain distinct in the service contracts.
- Chat, profile, notification, consent, manual verification, payment, safety and account lifecycle have substantial code, but do not uniformly satisfy the broader SRS flow. Detailed exceptions follow.

**SRS modules:** 30 | **Roadmap items:** 2 | **Feature rows:** 423 | **Feature-status counts:** 126 IMPLEMENTED, 229 PARTIAL, 41 UI PLACEHOLDER, 23 DISABLED, 2 NOT IMPLEMENTED, 2 ROADMAP; zero FRONTEND ONLY, BACKEND ONLY, or NEEDS VERIFICATION rows in the feature matrix.

## 2. Audit Method

Read all 22 PDF pages and extracted every feature/element table. Traced Flutter screens/actions/repositories to mounted Express routes, controllers/services, Sequelize models/migrations and existing tests. No tests were run. Source filenames/class/function names are evidence; tests are not treated as implementation. Production credentials and external provider acceptance are not inferred from code. A group heading receives `UI PLACEHOLDER` because it is a visual section label, not an independent feature. `NEEDS VERIFICATION` is reserved for claims that cannot be established from checked-out source or require deployment/provider evidence.

## 10. Match Engine

The actual `MATCH_ENGINE_VERSION` is v2 in `Backend/src/services/matchEngineService.js`. Weights: interests 35, relationshipGoals 25, communicationStyle 10, languages 10, city 5, smoking 5, drinking 5, weed 5. List similarity is shared count divided by the larger supplied list; exact factors are equality. Score normalizes across available factors and anchors unknown coverage at neutral 50; missing optional fields are not a negative signal. Coverage is available weight / 100.

Eligibility: completed profile, active account, not self, no previous action, not blocked, not already matched, reciprocal gender preferences, configured age bounds and stored enabled filters; optional verified, online, prompt, event-interest and minimum compatibility predicates. Discover ranking is compatibility descending then candidate user ID ascending. AI endpoint ranks eligible results by aiMatchScore descending, aiConfidence descending, candidate user ID ascending, then slices pages. Discover feed uses DB offset/limit+1; AI loads all eligible rows then slices in memory, with no snapshot/cursor guarantee.

Distance is not an eligibility or ranking input. Score factors do not include height, occupation, education, hometown, religion, community, pronouns, sexuality, smoking preferences beyond exact lifestyle field, prompt answers, event attendance or GPS. City is a low-weight exact compatibility factor. SRS compatibility help text must match these actual inputs and weights.
